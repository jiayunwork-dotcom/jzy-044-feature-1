这套传质高度核算后端至今只会做一个方向的事：把一组已经定死的操作条件喂进去，回一个填料层高度出来。工艺组真正头疼的场景是反过来的：塔已经在那儿了，或者塔还没定型但分离指标先被甲方钉死，问题永远是"为了达到这个分离要求，吸收剂到底得给多少、塔得做多高"。现在这件事全靠人手动试：先猜一个液相流量，跑一遍看看出口纯度够不够、算出来的高度能不能接受，不行再改一个数字重跑，来来回回七八轮。这一版要把这层反解能力做进服务，让它能接过一个分离目标，自己把满足目标的操作点算出来，而不是只当一台被动的正算器。

反解要覆盖两类工艺组最常问的诉求。第一类是定分离、求吸收剂用量：塔的几何、传质性能、进气条件、平衡关系都给定，只把出口气相分率作为要达成的指标（可以直接给目标出口分率，也可以给要求脱除的百分比，由服务换算），要反求出恰好满足这个指标所需的液相摩尔流量，以及在这个流量下对应的填料层高度。第二类是定塔高、求可行操作：塔几何与进气固定、填料层高度被现场条件卡死为一个上限，问在不超过这个高度的前提下，能达到的最好出口分率是多少、对应要配多大的液相流量。两类诉求共用同一套物理内核，差别只在"把哪个量当已知、把哪个量当要解的未知"。

反解在数学上是一个单调求根问题，服务必须自己完成迭代收敛，而不是丢给调用方去试。要解的那个操作变量（液相流量或与之等价的液气比）和分离效果之间存在单调关系：吸收剂给得越多，操作线离平衡线越远，推动力越足，同样塔高能达到的分离越深、或达成同一分离所需的塔越矮。服务要利用这个单调性稳定地把解夹住并收敛到给定精度，收敛判据、最大迭代次数这些都要能配置并在超限时如实报告，绝不能返回一个没真正收敛的数糊弄过去。解出来之后，必须用现有的正算内核在这个解点上复算一遍并把完整的正算结果一并给出，让调用方能一眼看出"按这个解跑出来的高度、传质单元数、离夹点的距离"确实和目标对得上。反解的结果和正算的结果必须自洽，不允许两条路径算出互相矛盾的数。

这里最容易翻车、也最能区分做得糙和做得稳的，是可行性边界。分离目标不是随便给什么都有解：要求的脱除深度一旦逼近由进气条件和平衡线决定的理论极限，所需吸收剂用量会趋于无穷、对应塔高发散，这正是原有服务里那个夹点。反解遇到"目标压根够不着"的情形——比如要求的出口分率低于该套平衡关系在无穷吸收剂下的理论下限、或要求的塔高连理论最小值都不够——必须明确判成目标不可行并说清楚为什么、缺口在哪（比如目标比可达极限还深多少，或给定塔高比达成该目标的最小塔高还差多少），而不是硬吐一个贴着夹点的巨大数字或者一头扎进迭代不收敛。反过来，如果给的目标松到随便一点吸收剂就能满足，也要老实返回那个偏小的解，不去无谓地加码。可行与不可行之间的那条边界要判得干净，恰好落在极限上时的处理要和原有夹点判定的口径一致，不能自成一套。

这几条关系要能被自动化测试逐条钉住：反解出的操作点用正算内核复算，得到的分离指标必须和当初给的目标在容差内吻合；把分离目标定得更苛刻一档，反解出的吸收剂用量必须单调变大、可行的塔高必须变高；把目标设到理论极限以外，必须稳定地报不可行而不是超时或返回垃圾数；对那个内置的、可手算核对的示范工况反解，结果要落在能手工验证的范围内。这些性质都要写成测试守住，而不是靠人跑一遍看着像对就算数。

反解能力同样只经 HTTP 对外提供，既要能对单组目标做一次反解，也要能一次提交一批分离目标逐条反解，其中个别目标不可行或参数非法时该条给出说明、其余照常算完互不牵连，这套逐条隔离的行为要和服务已有的批量口径保持一致。反解也要能像正算那样点名一个已登记的具名工况档来提供塔几何与传质参数底座、再在其上叠加本次的分离目标与要固定的量，不必每次重报全套参数。范围仍限定在这套气液传质高度核算上，只经 HTTP 提供接口，不做前端页面，也不涉及账户与权限，运行时环境固定为 Python 3.12，整套服务连同新增能力仍以容器方式构建、拉起并对外暴露接口，随附覆盖上述单调性、自洽性与不可行判定的自动化测试。
